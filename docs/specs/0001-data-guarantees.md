# SPEC-0001: Гарантии достоверности данных и контракт сигнала

**Статус:** Согласовано · **Обновлено:** 2026-10-12 · **Реализуется в:** SPEC-0004, 0005, 0006, 0008

## Зачем

ClusterSource полностью отвечает за чистоту и полноту данных: робот не
проверяет данные сам и опирается на то, что сигнал ClusterSource заслуживает
доверия.

Факты на 2026-10-12:

- В потоке T-Invest нет номера сделки (`Trade` v1.49: figi, direction, price,
  quantity, time, instrument_uid, trade_source), поэтому в реальном времени
  полноту ленты доказать нечем.
- Независимый источник — лента Мосбиржи (ISS) с номерами сделок — бесплатно
  доступна с задержкой 15 минут (проверено: в 19:35:56 МСК последняя сделка
  19:20:56).
- Сверка SBER с дневными итогами Мосбиржи (сделки в биржевые часы) показала,
  что данные молча неполны:

  | День | Доля сделок от биржевых |
  |------|------------------------|
  | 2026-09-03, 09-04 (из архива) | 1.00 (совпадение сделка в сделку) |
  | 2026-09-17, 09-29 | 0.99 |
  | 2026-09-21, 10-02 | 0.71–0.72 |
  | 2026-10-06, 10-08, 10-09 | 0.57–0.60 |
  | 2026-09-10 | 0.25 |
  | 2026-10-05 | 0.03 |

  Ни один из этих дней не был помечен как неполный.

Обещать «сигнал всегда верен в момент выдачи» нельзя. Можно гарантировать
три вещи ниже — о них договорились 2026-10-12.

## Делаем / Не делаем

**Делаем:**
- три гарантии G-1…G-3;
- статус качества данных по каждой минуте каждого инструмента;
- конверт сигнала с итогом проверки (`SIGNAL_CONFIRMED` / `SIGNAL_REVOKED`);
- события качества данных по инструменту (`DATA_DEGRADED` / `DATA_RESTORED`);
- режим наблюдения: статистику отзывов сигналов.

**Не делаем:**
- не обещаем полноту ленты в момент выдачи сигнала (физически недоказуемо без
  номеров сделок в реальном времени);
- не покупаем платную подписку Мосбиржи — обходимся бесплатными данными
  (решение 2026-10-12);
- не принимаем торговых решений за робота: политика ниже — рекомендация.

## Гарантии

- **G-1. Нет сигнала на известной проблеме.** ClusterSource НЕ ДОЛЖЕН выдавать
  сигнал по инструменту, если в окне данных сигнала есть минута со статусом
  `DEGRADED` или `GAP`, либо инструмент в текущий момент в состоянии
  `DEGRADED`.
- **G-2. Каждый сигнал проверяется.** Каждый выданный сигнал ДОЛЖЕН получить
  итог `SIGNAL_CONFIRMED` или `SIGNAL_REVOKED` не позднее `T_verify = 20 минут`
  после конца окна данных сигнала. Если проверить нечем (ISS недоступен), к
  сроку выдаётся `SIGNAL_REVOKED` с причиной `verification_unavailable`:
  непроверенный сигнал считается недоказанным.
- **G-3. Пороги только по окончательным данным.** Базовые уровни и пороги
  (RVOL, перцентили размера сделки, профили прошлых дней и т. п.) ДОЛЖНЫ
  считаться только по дням со статусом `FINAL` (SPEC-0006).

## Статус качества данных

Единица учёта — **(инструмент, минута UTC)**.

| Статус | Смысл | Кто ставит |
|--------|-------|------------|
| `PROVISIONAL` | Данные из стрима, проблем не замечено, сверки ещё не было | коллектор |
| `DEGRADED` | Детектор реального времени заподозрил проблему | SPEC-0004 |
| `VERIFIED` | Сверено с ISS, всё совпало; сделкам проставлен номер биржи | SPEC-0005 |
| `REPAIRED` | Сверено с ISS, расхождение исправлено сделками биржи | SPEC-0005 |
| `GAP` | Сверить или исправить не удалось (нет данных ISS) | SPEC-0005 |
| `FINAL` | День заменён ночным архивом и сошёлся с итогами биржи | SPEC-0006 |

Переходы: `PROVISIONAL|DEGRADED → VERIFIED|REPAIRED|GAP → FINAL`.
`DEGRADED` — подозрение. Окончательный вердикт по минуте выносит сверка.

Состояние инструмента в реальном времени — `OK` или `DEGRADED`. Смена
состояния публикуется событиями `DATA_DEGRADED` (с причиной) и `DATA_RESTORED`.

## Контракт сигнала

Сигнал (конверт):

| Поле | Описание |
|------|----------|
| `signal_id` | уникальный идентификатор |
| `type` | тип сигнала (SPEC-0008) |
| `class` | `fast` (живёт минуты) или `level` (уровень, живёт часы) |
| `ticker` | ключ хранения инструмента |
| `emitted_at` | время выдачи, UTC |
| `window` | `[from, to)` — данные, на которых посчитан сигнал |
| `quality` | статус данных окна на момент выдачи (обычно `PROVISIONAL`) |
| `bar_closed` | посчитан ли сигнал на закрытом баре |
| `payload` | параметры сигнала |

Итог проверки:

- `SIGNAL_CONFIRMED {signal_id}` — окно `VERIFIED`, либо окно `REPAIRED` и
  сигнал, пересчитанный на исправленных данных, сохраняется.
- `SIGNAL_REVOKED {signal_id, reason}`, где `reason`:
  `gap` — потеря данных без исправления;
  `repaired_changed_result` — на исправленных данных сигнала нет;
  `extra_trades` — в окне были лишние сделки (дилерские или дубли);
  `verification_unavailable` — к сроку `T_verify` проверить нечем.

`SIGNAL_REVOKED` означает «причина входа не доказана», а не «сделка будет
убыточной».

## Рекомендуемая политика робота

| Класс | Примеры | Рекомендация |
|-------|---------|--------------|
| `fast` | крупный агрессор, sweep, всплеск объёма | входить сразу; на `SIGNAL_REVOKED` закрыть позицию или перенести стоп в безубыток |
| `level` | stacked imbalance, поглощение на уровне, голый POC, value area | ждать `SIGNAL_CONFIRMED` |

**Режим наблюдения.** Первые 2–4 недели после запуска сигналов ClusterSource
считает долю `SIGNAL_REVOKED` по инструментам и причинам. По этой статистике
решается, торговать ли `fast`-сигналы сразу и нужна ли платная подписка.

## Поведение

**Сценарий: проблема известна до сигнала**
- Дано: по SBER детектор перевёл инструмент в `DEGRADED` (тишина потока).
- Когда: детектор сигнала находит паттерн по SBER.
- Тогда: сигнал не выдаётся (G-1). Отказ попадает в счётчик подавленных сигналов.

**Сценарий: подтверждение**
- Дано: сигнал по окну 10:00–10:05 выдан как `PROVISIONAL`.
- Когда: в 10:20 сверка с ISS дала `VERIFIED` для всех минут окна.
- Тогда: выдаётся `SIGNAL_CONFIRMED` не позднее 10:25 (G-2).

**Сценарий: дыра исправлена, сигнал исчез**
- Дано: сигнал выдан, в окне сверка нашла недостающие сделки и дозалила их (`REPAIRED`).
- Когда: детектор, пересчитанный на исправленных данных, сигнала не находит.
- Тогда: `SIGNAL_REVOKED(reason=repaired_changed_result)`.

**Сценарий: ISS недоступен**
- Дано: ISS не отвечает с 10:00.
- Когда: наступает срок `T_verify` для сигнала с окном до 10:05.
- Тогда: `SIGNAL_REVOKED(reason=verification_unavailable)` не позднее 10:25.

## Данные и контракты

- Таблица статусов качества по минутам — в SQLite инструмента, доступ только
  через `MarketDataRepository` (инвариант A1).
- Контракт сигналов и событий качества — новый файл
  `docs/contracts/asyncapi/cluster-source-signals.asyncapi.yaml` (при
  реализации SPEC-0008). Канал доставки роботу выбирается в SPEC-0008.

## Наблюдаемость

- Метрики: доля `SIGNAL_REVOKED` по инструменту и причине; задержка
  выдачи итога проверки; число подавленных по G-1 сигналов; доля минут по
  статусам за день.
- Каждый `DATA_DEGRADED` логируется с инструментом, причиной и временем.

## Приёмка

| № | Критерий | Тест |
|---|----------|------|
| A-1 | При `DEGRADED` в окне сигнал не выдаётся | при реализации SPEC-0008 |
| A-2 | Итог проверки выдаётся каждому сигналу не позднее `T_verify` | при реализации SPEC-0005/0008 |
| A-3 | При недоступном ISS к сроку выдаётся `verification_unavailable` | при реализации SPEC-0005 |
| A-4 | Расчёт порогов читает только `FINAL`-дни | при реализации SPEC-0006/0008 |
