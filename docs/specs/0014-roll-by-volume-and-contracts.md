# SPEC-0014: Ролл по объёму и хранение двух ближайших контрактов

**Статус:** Черновик · **Обновлено:** 2026-10-19 · **Зависит от:** SPEC-0003, 0005, 0006, 0009, 0012, 0013

## Зачем

Непрерывный фьючерс (`Si_CONTINUOUS` и др.) на каждый день берёт один
контракт — ближайший по `last_trade_date` (`config.nearest_contract`,
SPEC-0013). Сделки остальных контрактов того же актива не сохраняются вовсе.

**Доля ближайшего контракта в объёме актива** (лента ISS, контракты без
календарных спредов):

| Актив | Ближайший | 16.10 | 19.10 |
|-------|-----------|-------|-------|
| Si, RI, MX, CR, GD, SR | Z6 | 97,6–99,4% | Si 98,4% |
| Eu | EuZ6 | 94,9% | — |
| BR | BRX6 | 94,1% | 93,2% (17.10 — 79,7%) |
| NG | NGV6 | 80,8% | **61,6%** (NGX6 — 35,4%) |

**На ролле потери большие.** Доля следующего контракта по дневным итогам ISS
(`iss_day_totals`) в последние дни старого:

| Актив | Последний день торгов L | L−3 | L−2 | L−1 | L |
|-------|------------------------|-----|-----|-----|---|
| Si (U6→Z6) | 17.09 | 42% | 43% | 44% | 79% |
| RI | 17.09 | 14% | 20% | 37% | 76% |
| MX | 17.09 | 19% | 25% | 40% | 74% |
| CR | 17.09 | 29% | 34% | 40% | 80% |
| SR | 17.09 | 27% | 31% | 42% | 70% |
| GD | 18.09 | 19% | 36% | 73% | 94% |
| BR (U6→V6) | 31.08 | 26% | 28% | 40% | 88% |
| BR (V6→X6) | 01.10 | 25% | 36% | 64% | 97% |
| NG (U6→V6) | 28.09 | 25% | 30% | 41% | 96% |

В последний день торгов `L` склейка держит истекающий контракт, у которого
3–30% объёма актива: кластеры этого дня почти пусты. В дни до `L` во втором
контракте теряется до 45% объёма.

**Что есть в других источниках.** Лента ISS (`_iss/forts`, SPEC-0003) хранит
сделки всех контрактов, но только с 12.10, без хвоста вечерней сессии
(SPEC-0011) и не проходит наши проверки. Архив T-Invest (`history-trades`)
отдаёт любой контракт за любой прошедший день — потерянное восстановимо.

**Почему одного «объёма предыдущего дня» мало.** Объём следующего контракта
обгоняет текущий впервые в день `L` (7 из 9 роллов выше) или за день до него
(GD 17.09, BR 30.09). Решение на день D по объёму дня D−1 переключает в день
`L+1` — то же, что сейчас. Поэтому правило дополнено: в последний день торгов
активен уже следующий контракт (в таблице — 70–97% объёма в день `L`).

## Делаем / Не делаем

**Делаем:**
- активный контракт непрерывного фьючерса — по объёму предыдущего торгового
  дня, не позже последнего дня торгов текущего; решение на день принимается
  один раз и хранится;
- отдельное хранение двух ближайших контрактов каждого актива
  (`SiZ6`, `SiH7`) с полным циклом: стрим, догрузка, архив, сверка, FINAL;
- пересчёт склейки по новому правилу для всех уже сохранённых дней
  и перекачку дней, где контракт сменился.

**Не делаем:**
- бессрочные фьючерсы (`USDRUBF`, `CNYRUBF`, `IMOEXF`, `GLDRUBF`, …) — по
  решению владельца отложено, это отдельные инструменты;
- склейку с поправкой цены (back-adjust) — склейка остаётся «как торговалось»,
  скачок цены на ролле закрывается отметкой `contract_roll` (SPEC-0004);
- сигналы по хранилищам контрактов — сигналы и нормы только у непрерывного
  инструмента (SPEC-0008);
- календарные спреды — их сделок нет в анонимной ленте (SPEC-0011 G-4).

## Правила

**Торговый день.** Торговый день FORTS D — 06:50–23:50 МСК календарного дня D
(лента ISS 15–16.10: SiZ6 06:59–23:44, `TRADE_SESSION_DATE` = D) и целиком
лежит внутри суток D UTC. Смена контракта всегда приходится на ночь без
торгов.

**Активный контракт на день D.** `C` — активный контракт дня D−1 (нет решения
за D−1 — `nearest_contract(D)`, SPEC-0013). `N` — следующий контракт актива:
ближайший по `last_trade_date` после `C`. По порядку:

1. `C.last_trade_date` < D → ближайший контракт с `last_trade_date` ≥ D
   (истёк, SPEC-0013 G-1); причина `expired`.
2. `C.last_trade_date` = D → `N`; причина `last_day`.
3. P — предыдущий торговый будний день по календарю ISS (SPEC-0012; сессии
   выходных пропускаются — у них малый и случайный объём). Объём `N` за P
   больше объёма `C` за P → `N`; причина `volume`.
4. Иначе `C`; причина `carry`.

Переход по объёму — только на второй ближайший контракт (`C` — ближайший).
Назад к более раннему контракту склейка не возвращается.

**Объём за P** — в контрактах, по ленте ISS за торговый день P, если лента дня
не отмечена `ISS_FEED_INCOMPLETE`; иначе по дневным итогам ISS
(`iss_day_totals`, кэш или запрос). Нет ни того ни другого — шаг 3
пропускается (`ROLL_NO_VOLUME`), переход по объёму откладывается на день.

**Когда принимается решение.** В ночном обслуживании (00:05 UTC, до догрузки)
на сегодня и на каждый сохранённый день без решения; затем стрим
переподключается с `resolve=True`, как сейчас. При запуске, если решения на
сегодня нет, его принимает разрешение FIGI стрима — только по локальным данным
(лента, кэш итогов), без сети: стрим не ждёт ISS (SPEC-0011 G-5). Принятое
решение не пересматривается.

**Одно правило для всех.** Стрим, догрузка (`archive_key_candidates`,
`current_figi`), FINAL (`secid`), сверка (`ticker`) и `reader.get_contract`
берут контракт дня из сохранённого решения, а не вызывают `nearest_contract`.

**Хранилища контрактов.** Для каждого непрерывного фьючерса отдельно хранятся
`futures_contracts` (по умолчанию 2) ближайших по `last_trade_date` ≥ D
контрактов дня D. Активный контракт всегда среди них (правило выше не уходит
дальше второго). Хранилище — тикер контракта (`data/history/SiH7/…`), тип
`futures_contract`, `tick_size`/`lot_size` — от актива.

- **Окно контракта** — дни D от первого сохранённого дня непрерывного
  инструмента, в которые контракт входит в число ближайших. Вне окна данных
  у хранилища нет и пропуски не ищутся.
- В окне — полный цикл обычного инструмента: стрим (FIGI ближайшего
  контракта ведёт и в непрерывный, и в хранилище контракта — маршрут хаба
  «FIGI → несколько хранилищ», так же `instrument_uid` для открытого интереса),
  догрузка, архив, сверка с лентой ISS по своему `secid`, детекторы деградации,
  пропуски по календарю (SPEC-0013 G-2), FINAL по ленте ISS своего `secid`.
- После окна подписки нет; обслуживание (архив, FINAL) продолжается, пока
  у хранилища есть горячие строки или дни без итогового вердикта
  в пределах `history_check_days`.
- Явный `futures_contract` в `config.yaml` с тем же тикером — ошибка конфига
  при запуске (два источника одного хранилища).
- Каталог `SRZ6` (остаток ручного `futures_contract`, 7 дней 23.08–04.09)
  становится хранилищем контракта SRZ6 и проверяется как остальные.

**Перевод истории.** Первое обслуживание после выпуска принимает решения для
всех сохранённых дней каждого непрерывного фьючерса (с 08.08, по итогам ISS).
День, где новый контракт отличается от прежнего (`contract:D` сверки, иначе
`nearest_contract`), отмечается для перекачки `roll_rule` (окном не
ограничен), перекачивается из архива; вердикт пересчитывается по SPEC-0006
G-6. По симуляции выше это день `L` каждого ролла и дни раннего перехода
(GD 18.09, BR 01.10) — около 15 дней. Хранилища контрактов догружаются из
архива за свои окна тем же обслуживанием.

## Гарантии

- **G-1.** Активный контракт дня ДОЛЖЕН определяться один раз, храниться и быть
  одним для стрима, догрузки, сверки, FINAL и читателя; принятое решение НЕ
  ДОЛЖНО меняться задним числом.
- **G-2.** Склейка ДОЛЖНА переходить на следующий контракт не позже
  последнего дня торгов текущего, а раньше — когда объём следующего за
  предыдущий торговый будний день больше; НЕ ДОЛЖНА возвращаться к более раннему
  контракту и уходить дальше второго ближайшего.
- **G-3.** Каждая биржевая сделка двух ближайших контрактов актива в окне
  контракта ДОЛЖНА храниться в его хранилище и проходить те же проверки, что у
  любого инструмента (SPEC-0004, 0005, 0006, 0013 G-2).
- **G-4.** Сохранённые дни, контракт которых по новому правилу другой, НЕ ДОЛЖНЫ
  оставаться прежними: отметка `roll_rule` и перекачка.

## Поведение

**Сценарий: ролл Si в декабре**
- Дано: активен SiZ6, `last_trade_date` SiZ6 = 17.12 (чт).
- Когда: 14.12 объём SiH7 ещё меньше SiZ6, 15.12 — больше.
- Тогда: 15.12 — SiZ6 (`carry`, по объёму 14.12); в 00:05 UTC 16.12 решение
  по объёму 15.12 — SiH7 (`volume`), лог `ROLL`, отметка `contract_roll` при
  переподключении. Без перехода по объёму — SiH7 с 17.12 (`last_day`).

**Сценарий: запуск без ленты за вчера**
- Дано: коллектор не работал вчера, решения на сегодня нет, итогов в кэше нет.
- Когда: запуск.
- Тогда: шаг 3 пропущен, контракт вчерашнего решения (или по SPEC-0013),
  WARN `ROLL_NO_VOLUME`; решение сохраняется и не пересматривается.

**Сценарий: новый контракт входит в окно**
- Дано: SiZ6 истёк 17.12, ближайшие 18.12 — SiH7 и SiM7.
- Когда: 18.12 00:05 UTC обслуживание.
- Тогда: появляется хранилище `SiM7`, стрим после переподключения подписан на
  SiH7 (непрерывный + `SiH7`) и SiM7; `SiZ6` без подписки, обслуживается до
  итогового вердикта.

## Данные и контракты

- Новая таблица в SQLite непрерывного инструмента — `active_contract(day TEXT
  PRIMARY KEY, ticker TEXT NOT NULL, reason TEXT NOT NULL, basis TEXT, decided_at
  TEXT NOT NULL)`; `reason` ∈ `initial`, `carry`, `volume`, `last_day`,
  `expired`; `basis` — сравнение объёмов («SiH7 523 104 > SiZ6 410 220 за
  2026-12-15, лента»). Доступ — через `MarketDataRepository` (запись только
  если строки нет).
- `reader.get_contract` читает `active_contract`; `meta['contract:D']` сверки
  больше не пишется (остаётся источником «прежнего» контракта для перевода
  истории).
- Новая причина перекачки `roll_rule` в `days_to_refresh`.
- Конфиг: `futures_contracts: 2` (верхний уровень; 0 — без хранилищ
  контрактов).
- Подписки стрима: +1 FIGI на актив (13), всего ≈ 71 из 300 (SPEC-0009).
- Диск: хранилище ближайшего контракта дублирует непрерывный (все
  `*_CONTINUOUS` за 68 дней — 836 МБ), второй контракт — ещё ~5%.

## Наблюдаемость

- `ROLL X D: A -> B (объём P: B n > A m, лента|итоги)` (INFO), `ROLL X D: A -> B (последний день торгов A)` (INFO), `ROLL X D: A -> B (истёк)` (INFO).
- `ROLL_NO_VOLUME X D: нет объёмов за P — остаётся A` (WARNING).
- `CONTRACT_WINDOW X: хранилища Y, Z` (INFO, при каждом разрешении FIGI).
- Перевод истории: `ROLL_RULE X D: A -> B, отмечен для перекачки` (WARNING) по
  каждому дню.

## Открытые вопросы

- [ ] Хранить ли ближайший контракт отдельно, раз он дублирует непрерывный
  (~+12 МБ/день)? Альтернатива — непрерывный как «представление» над
  хранилищами контрактов по таблице `active_contract`: без дубля, но
  переделка FINAL, сверки, качества и сигналов. Предложение — дубль.
- [ ] Перекачивать ли историю (G-4) или вести новое правило с даты выпуска?
  Предложение — перекачивать: нормы сигналов (SPEC-0008) строятся по дням
  склейки, правило должно быть одно на весь ряд.

## Журнал решений

- **2026-10-19** — Владелец продукта: ролл по объёму предыдущего дня и
  отдельное хранение двух ближайших контрактов; бессрочные фьючерсы — позже.
- **2026-10-19** — Симуляция на итогах ISS (9 роллов 31.08–01.10): объём
